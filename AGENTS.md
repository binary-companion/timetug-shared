# timetug-shared agent guide

## What this is

The portable logic shared by every TimeTug front end, as a Rust workspace: `timetug-core` and `timetug-bridge`, the engine (`timetug-engine`, `timetug-engine-protocol`) and its C interface (`timetug-engine-c`, which builds `TimeTugEngineC.dll`, `libTimeTugEngineC.dylib` and `libTimeTugEngineC.so`), with the .NET wrapper (`dotnet/TimeTug.Engine`) that ships it as the NuGet package `TimeTug.Engine`. It builds on macOS, Linux, Windows x64 and Windows ARM64. UI, Apple frameworks and platform adapters never live here. This is the `v2` branch: the Swift package this library started as is gone from it (see "On v2: Rust"); `main` still holds it and releases 1.x until `v2` replaces `main`.

## Repositories

- `calendar-connectors`: the connector library. This repository depends on it by git tag (`[workspace.dependencies]` in `Cargo.toml`, `Cargo.lock` committed).
- `timetug-shared` (this repository): released as `X.Y.Z` tags (and, on `v2` before 2.0.0, as `2.0.0-alpha.N` prereleases).
- `timetug`: the Mac app; pins this repository exactly in `Apps/macOS/project.yml` (key `TimeTugShared`), and receives a bump pull request from every release here.
- `timetug-windows` (later): the WinUI app.

Dependency direction: `calendar-connectors` <- `timetug-shared` <- the apps.

## Rules

- Core never reads the clock (`now: Timestamp` is passed in); `scripts/ci/check-no-clock.py` enforces it for the pure crates. Test each behaviour, failing test first.
- The crate dependency table is `ALLOWED` in `scripts/ci/check-crate-architecture.py`; no crate may depend on a platform API or a UI framework.
- `Cargo.lock` is changed by `cargo` in a reviewed pull request, or for the connector pin by `scripts/ci/bump-cargo-dependency.py` (the bump workflow). `include/timetug_engine.h`, `dotnet/TimeTug.Engine/**` and `dotnet/TimeTug.Engine.Tests/**` change only with the `semver:major` label or additively.

## Backward compatibility

Owner rule (2026-10-16): within a major version, a release of this library must drop into an existing front end with no change to that front end; front ends are not released when the library is, and their releases stay owner-initiated. Additions are allowed. Removing, renaming or retyping anything, or changing a value or a meaning, needs the pull request label `semver:major` (which also makes the release a major version).

"Additive" has one exact meaning for JSON here: the new value is a superset of the baseline's. Every member of a baseline object is present with an equal value (recursively); objects may gain members; arrays keep their length and compare element by element under the same rule; any other value is equal and of the same JSON type (a number stays a number, `null` stays `null`).

On every pull request the `compat` and `compat-dotnet` jobs of `ci.yml` compare with the baseline, the highest `X.Y.Z` tag reachable from the base branch (`scripts/ci/compat/compat.py`; its tests are `scripts/ci/tests/test_compat.py`). On `v2` that is the last 1.x tag reachable from it (1.8.1): the point is that every 1.x contract file keeps passing in the Rust library. There are five checks (the sixth of the Swift days, the Swift public API diff, ended with the Swift sources):

1. Wire contract: the baseline's `Conformance/Fixtures/golden` run through the fixture tests (`TT_BASELINE_FIXTURES=<dir> cargo test -p timetug-engine-protocol fixture`): each fixture is decoded with the current code (into its wire type where it has one) and re-encoded, and the result must be a superset of the baseline JSON. The current fixtures keep the exact round trip. A baseline fixture file may be edited only additively (superset); deleting or renaming one fails.
2. Old front end, new backend: the baseline's `Conformance/Scenarios` (with `data/`) run through the C interface (`TT_BASELINE_SCENARIOS=<dir> cargo test --release -p timetug-engine-c --test scenarios`). A baseline scenario or data file may be edited only additively, except that its arrays (steps, expectations) may also gain entries at the end; changing, removing or inserting before an existing entry, or deleting the file, fails.
3. C ABI: the declarations in `include/timetug_engine.h` (comments and spacing aside) are unchanged, and the built release library (`target/release`) still exports the baseline's `tt_engine_*` functions.
4. Persisted data: the Mac-format fixtures model files on users' disks, so they are strictly add-only: an existing file never changes, even additively. They lived in `Tests/TimeTugEngineTests/Fixtures` at the baseline and live in `fixtures/engine/` now; a baseline file must exist byte for byte at either path (`compat.py frozen ... --strict Tests/TimeTugEngineTests/Fixtures=fixtures/engine fixtures/engine`). The tests that load them keep passing.
5. .NET: `dotnet pack` with package validation (`-p:TimeTugPackageValidationBaseline=<version>`) against the latest TimeTug.Engine on nuget.org.

With the `semver:major` label each check is skipped with a notice; the checks are also skipped on pushes and before the first release. Adding or removing a label re-runs CI.

## Verify

`cargo fmt --all --check && cargo clippy --workspace --all-targets --locked -- -D warnings && cargo test --workspace --locked && cargo deny check`, `c-smoke/run.sh` and `c-harness/run.sh` (the C interface library against the header, then the concurrency harness), `python3 scripts/ci/check-crate-architecture.py`, `check-tokio-features.py`, `check-no-clock.py`, `check-test-parity.py --require-complete ...` and `check-third-party-notices.py` (regenerate the notices with `scripts/dev/generate-third-party-notices.py`), `scripts/ci/check-repository-contracts.py`, the tests under `scripts/ci/tests` (`python3 -m unittest discover -s scripts/ci/tests -p 'test_*.py'`, with PyYAML from `scripts/ci/requirements-test.txt`) and `scripts/release/tests` (`test-next-version.sh`, `test-release-version-step.sh`, and `python3 -m unittest discover -s scripts/release/tests -p 'test_*.py'`), `scripts/ci/tests/test-bump-workflow-step.sh`, and for the wrapper `TIMETUG_ENGINE_LIBRARY=$PWD/target/release/libTimeTugEngineC.dylib dotnet test dotnet/TimeTug.Engine.Tests -c Release` (`.so` on Linux). In CI these are the jobs `macos`, `linux`, `windows-x64`, `windows-arm64`, `rust-lint`, `rust-targets`, `architecture`, `compat`, `compat-swift`, `compat-dotnet`, `swift-bindings`, `kotlin-bindings` and the `dotnet-*` jobs; the CI job ids are the required status checks, `check-repository-contracts.py` fails when one disappears.

## Release flow

Do not tag by hand. A merge to `main` runs `release.yml`: the `semver:*` labels pick the bump, the workflow tags and publishes, appends "Built and tested with calendar-connectors X.Y.Z" (the tag `scripts/ci/cargo-dependency-version.py Cargo.lock calendar-connectors` prints) to the release notes, then its `notify` job (environment `bump`, the `timetug-bot` token) dispatches `library-released` (`library` `timetug-shared`, `version` `X.Y.Z`) to `timetug`. `timetug` opens a "Bump timetug-shared to X.Y.Z" pull request that moves the `TimeTugShared` pin and raises its `CalendarConnectors` pin to at least the version this repository's `Cargo.lock` records, so the app and the engine run the same connector version. The native library is built per Windows architecture with `cargo build --release --locked -p timetug-engine-c --target <triple>` and `TIMETUG_ENGINE_VERSION` set to the version (it is `ready.engineVersion`); the NuGet package `TimeTug.Engine` carries exactly one native file per architecture and is pushed with trusted publishing. The agent never merges or publishes; the owner does.

Prereleases (on `v2`, before 2.0.0): the owner dispatches `Release` on ref `v2` with the input `prerelease`, for example `gh workflow run Release --repo binary-companion/timetug-shared --ref v2 -f prerelease=alpha.1`. The version is `2.0.0-<prerelease>` (`scripts/release/next-version.sh --prerelease`), the tag is created on the `v2` commit, the GitHub release is marked as a prerelease, the package is pushed as a prerelease version, and no `library-released` dispatch is sent. The input is refused on any other ref, with a version input, for a tag that exists on another commit, and once a stable 2.x release exists. The environments `publish` and `bump` must allow the `v2` branch (a repository setting the owner changes).

### Releases and release commits (the Swift package)

The Mac app (and any Swift host) depends on this repository by URL and tag: the root `Package.swift` declares the product `TimeTugKit` (sources in `swift/TimeTugKit/Sources`) over a binary target. On a branch that target is a **path** (`build/TimeTugEngineFFI.xcframework`, built by `scripts/dev/build-xcframework.sh`). A release of `X.Y.Z` does this, in order: `publish` computes the version and creates a **draft** GitHub release; `swift-package` (macOS) builds the XCFramework with `TIMETUG_ENGINE_VERSION`, zips it as `TimeTugEngineFFI-X.Y.Z.xcframework.zip`, computes `swift package compute-checksum` and rewrites `Package.swift` with `scripts/release/write-swift-package.py` (the path becomes the release asset URL and the checksum); `release-swift` uploads the asset to the draft, makes the **release commit** through the API (parent: the released `main` or `v2` commit; its only change is `Package.swift`), tags that commit `X.Y.Z` (SwiftPM resolves tags, and the tag is on no branch) and publishes the release; only then do `notify` and the NuGet push run. The Mac pins `X.Y.Z` in its `Package.swift` or `Package.resolved`. The NuGet package is built from the same source commit.

"The latest release of a branch" is defined by `scripts/release/release-tags.py` and nowhere else: a strict `X.Y.Z` tag belongs to a ref when its commit is an ancestor of the ref, or when it is a release commit (one parent, the only changed file is `Package.swift`) whose parent is an ancestor. `release.yml` (the latest version, the "already tagged" guard, the label walk) and `scripts/ci/compat/compat.py` (the baseline) call it. Never use `git tag --merged` or `git describe` to find the latest release: they cannot see release commits. Dry run: `gh workflow run Release --ref <branch> -f publish=false` builds the XCFramework and the rewritten `Package.swift` and uploads them as the artifact `swift-package-<version>`, without any tag or release.

## Dependents and the bump chain

The chain is live and was proven by a drill on 2026-10-15: a `calendar-connectors` release dispatched to `timetug` and to this repository; this repository's bump pull request ("Bump calendar-connectors to X.Y.Z", from `.github/workflows/bump-dependencies.yml`) was merged and released a new `timetug-shared`; `timetug` then opened its own "Bump timetug-shared to X.Y.Z", which moved both pins and closed the two older bump pull requests as superseded.

- `calendar-connectors` release: the dispatch arrives here, and `bump-dependencies.yml` opens the connector bump (see CI workflows below). (`repository_dispatch` always runs the default branch's copy of the workflow; on `v2` the bump is started by hand, below.)
- `timetug-shared` release: `release.yml` notifies `timetug` (above). Nothing else depends on this repository yet.
- Recover a missed dispatch for `timetug`: `gh workflow run "Bump dependencies" --repo binary-companion/timetug -f library=timetug-shared -f version=X.Y.Z`. Recover one for this repository (connector versions only): `gh workflow run "Bump dependencies" --repo binary-companion/timetug-shared --ref <branch> -f version=X.Y.Z` (the pull request goes to that branch; on `v2` the version may be `2.0.0-alpha.N`). Locally: `python3 scripts/ci/bump-cargo-dependency.py <version>`. A failed `notify` job can also be re-run alone from this repository's Actions page; the workflows are idempotent, so a repeat opens nothing new.

## On v2: Rust

The `v2` branch holds the Rust port of this library (Rust engine program; design, conventions and tracker are in the `timetug` repository under `docs/superpowers/`). Since phase 3 task 10 the Swift package is gone from it: the sources, `Package.swift`, the Swift CI jobs and scripts, and the vector exporter. The last commit that still had both languages is recorded in `docs/rust-port/README.md`; `main` keeps releasing the Swift library until `v2` replaces it.

- Bindings (`timetug-engine-ffi`, phase 5): the UniFFI crate for Swift and Kotlin. `uniffi` is pinned exactly (`=0.32.2`) and is a dependency of this crate only; it is MPL-2.0, allowed through per-crate exceptions in `deny.toml` (the notices carry the licence text). The generator binaries are built with `--features bindgen`; settings of the generated code are in `crates/timetug-engine-ffi/uniffi.toml`. What UniFFI can and cannot express, and the workarounds, are in `docs/bindings-spike.md`. Never enable the `uniffi` `tokio` feature (it starts a multi-thread runtime).
- Layout: a Cargo workspace at the root, one crate per former Swift product in `crates/` (`timetug-core`, `timetug-bridge`, `timetug-engine`, `timetug-engine-protocol`, `timetug-engine-c`, `timetug-engine-ffi`, `dedup-benchmark`). `timetug-engine-c` has `[lib] name = "TimeTugEngineC"`, so its files are `TimeTugEngineC.dll`, `libTimeTugEngineC.dylib` and `libTimeTugEngineC.so` (CI checks the names). The dependency table is `ALLOWED` in `scripts/ci/check-crate-architecture.py`. `Cargo.lock` is committed. `fixtures/engine/` holds the Mac-format persisted-data fixtures (moved from `Tests/TimeTugEngineTests/Fixtures`; byte-identical, add-only), `vectors/` the golden vectors the Rust tests replay (produced by the Swift code before it left; `vectors/README.md` says how they were made), `Conformance/` the golden fixtures and scenarios.
- Connector crates: depended on in `[workspace.dependencies]` by git (`calendar-connectors` on `v2`). Until the first connector prerelease is taken they are pinned by `rev`; afterwards by `tag` (`2.0.0-alpha.N`, then `tag = "2.0.0"`) through `scripts/ci/bump-cargo-dependency.py <version>`, which rewrites the lines and runs `cargo update -p` for the connector crates (it refuses a lower version, a change of major and anything but `X.Y.Z` or `X.Y.Z-alpha.N`). To build against a local checkout run `scripts/dev/use-local-connectors.sh <path>` (it writes the git-ignored `.cargo/config.local.toml`, which the tracked `.cargo/config.toml` includes); `--restore` deletes it. Never commit a `[patch]` section: `rust-lint` fails if a tracked cargo config has one.
- Core and Bridge (phase 2, done): `timetug-core` (model, takeover, dedup, store, agenda and widget) and `timetug-bridge` (`EventMapper`, `ConnectedSource`) are complete ports; every Swift test of `TimeTugCoreTests` and `CalendarBridgeTests` has a `ported` row in `docs/rust-port/test-parity.md` and `check-test-parity.py --require-complete` enforces it in `rust-lint`. Notes for hosts (the engine): `Calendar` parameters are `&Zone` (`CalendarStore::set_zone`), the store's `passClock` is a required `pass_clock` argument, `ConnectedSource::changes` calls `tokio::spawn` so it needs the engine's runtime, and `WidgetSnapshot` dates are ISO 8601 strings with whole seconds. Per-file deviations are in `docs/rust-port/file-map.md`; the dedup benchmark (`scripts/benchmarks/run-dedup.sh`) and its numbers are in `docs/rust-port/baselines.md`.
- Engine (phase 3 task 4, done): `timetug_engine::Engine` (`crates/timetug-engine/src/engine/`, six files following the `// MARK:` sections of `Engine.swift`; line ranges in `docs/rust-port/file-map.md`) is a complete port; every Swift test of `TimeTugEngineTests` has a `ported` row and `--require-complete TimeTugEngineTests` runs in `rust-lint`. For hosts: `Engine::new(host)` and every `Engine` method need a `tokio` runtime (the engine creates none and no thread); state is a `std::sync::Mutex<EngineInner>` that is never held across an `.await`, so a diagnostics sink or a `states()` / `events()` consumer must not call back into the engine synchronously; `states()` is a `watch::Receiver` (newest wins; `changed()` first returns the current state), `events()` an unbounded `mpsc` receiver per call (never dropped); both end on `stop`. Only `SystemClock` touches `tokio::time`.
- C interface (phase 3 tasks 5 to 8, done): `timetug-engine-c` owns one engine thread and one delivery thread per engine and exports the four `tt_engine_*` functions of the unchanged `include/timetug_engine.h`; `unsafe` appears only in `c_interface.rs` and `delivery.rs`. `c-smoke/` and `c-harness/` (ordered and coalescing callbacks, destroy from inside and outside a callback, stale handles, many engines) test the built library from C; `crates/timetug-engine-c/tests/scenarios.rs` runs `Conformance/Scenarios`.
- .NET package (phase 3 task 9, done): `dotnet/TimeTug.Engine` is unchanged C# over the C interface; `dotnet/pack/assemble-native.ps1` collects the one native DLL per architecture (exports and Windows-system-DLL-only dependencies checked, C runtime linked statically through `.cargo/config.toml`), `dotnet/pack/measure-size.ps1` applies the 8 MB per-architecture size gate (numbers in `docs/rust-port/size.md`), and `THIRD-PARTY-NOTICES.md` lists every crate of the library (`scripts/ci/check-third-party-notices.py`).
- Toolchain: pinned in `rust-toolchain.toml` (1.99.1, with rustfmt, clippy and the targets of design section 6.4), the same version as `calendar-connectors`; raise it only in a reviewed pull request, together with that repository. External crates are pinned exactly in `[workspace.dependencies]`; a crate not on the list of conventions section 3 needs a decision record, and `deny.toml` (the `allow` list), `EXTERNAL` in the architecture script and the pin must change together. `tokio` has only `rt`, `time`, `sync`, `macros` (`scripts/ci/check-tokio-features.py`). `timetug-core` and `timetug-bridge` never read the clock or the environment: every function that needs the time takes `now: Timestamp` (`scripts/ci/check-no-clock.py` fails on `Timestamp::now`, `SystemTime`, `Instant::now`, `Zoned::now`, `tokio::time` and `std::env` in their non-test code). `cargo-deny` is pinned at 0.20.2 in the `rust-lint` job of `ci.yml`.
- Re-check the vectors: `vectors/` was exported by the Swift code and is now frozen (the exporter left with the Swift sources; `vectors-current` and the weekly drift workflow are gone). The Rust tests replay it. A change in a zone rule, URL parsing or text folding that a new `jiff` or `url` version brings shows up as a failing vector test: investigate it, never regenerate the vector blindly.
- Rules for ported code: the conventions file `docs/superpowers/plans/2026-11-10-rust-port-conventions.md` in `timetug`. Open pull requests against `v2`; never push to `v2` or `main`.

## Finding code

- If your agent has a semantic code-index skill (in Claude Code and Codex, the `index` skill), use it in this repo without asking first; this is standing permission. At the start of a task check its status. If this checkout is not indexed, or files changed a lot since the last index, run the (incremental) index. A new checkout or worktree is seeded from the index that the `Code index` workflow publishes from `main` (artifact `qindex`, fetched with `gh`), so the first run only embeds what differs from `main` and takes seconds. Without a compatible published index a full build takes many minutes: start it in the background and keep working with grep until it finishes. Then search the index before broad grepping or reading many files, and read the hit ranges rather than trusting snippets. Use grep for exact identifiers and strings. `.qindexignore` lists paths the index leaves out.
- Without such a skill, start from `crates/` (one directory per crate) and grep.
- Exact references ("who uses or calls this?", definitions, implementations) come from Serena (symbol tools over rust-analyzer) when your agent has it; use it before grep.

## CI workflows

- `.github/workflows/index.yml` (`Code index`): on pushes to `main` builds the semantic code index incrementally from the previous `qindex` artifact against a throwaway Qdrant and publishes it as the `qindex` artifact (90 days) for agents' index skill. `scripts/dev/qindex.py` is a copy of the index skill's script (`~/.agents/skills/index/scripts/qindex.py`): keep the two identical (`diff` them) and keep the library versions in the workflow equal to the skill's. The export records the model and chunker version, and the skill refuses an index that does not match and builds locally instead.
- `.github/workflows/bump-dependencies.yml` (`Bump dependencies`): when `calendar-connectors` releases it sends `library-released`, and this workflow (environment `bump`, the `timetug-bot` token, repository `timetug-shared` only) opens a "Bump calendar-connectors to X.Y.Z" pull request that moves the connector git dependency in `Cargo.toml` and `Cargo.lock` through `scripts/ci/bump-cargo-dependency.py`, to the branch the workflow runs on. It applies no label (merging releases a patch version), never merges, and closes only same-repository bump pull requests for older versions. A missed dispatch is recovered with `gh workflow run "Bump dependencies" --ref <branch> -f version=X.Y.Z`. A major version change needs a manual pull request (the script refuses it). Its tests are `scripts/ci/tests/test_bump_cargo_dependency.py` and `scripts/ci/tests/test-bump-workflow-step.sh`.
- `.github/workflows/release.yml` (`Release`): see "Release flow". Its tests are `scripts/release/tests/` and `scripts/ci/tests/test_release_nuget_jobs.py`.
- `.github/workflows/bench.yml` (`Engine benchmark`): by hand; measures the Rust library with `dotnet/TimeTug.Engine.Bench` (numbers in `docs/rust-port/baselines.md`).
